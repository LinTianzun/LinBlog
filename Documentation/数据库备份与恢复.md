# 数据库备份与恢复

LinBlog 的图片以 `MEDIUMBLOB` 存在 MySQL 的 `image` 表里。只备份
`serve/data/files` 或回收站目录**不能**恢复站点，必须单独备份数据库本体。

本文档覆盖：备份原理、配置项、日常操作、隔离恢复演练和故障恢复。

---

## 1. 备份原理

备份由服务进程自己生成，不依赖 `mysqldump` / `mysql` 客户端，
因此容器镜像和 Windows 本地都能直接运行。

产物是 **gzip 压缩的 JSON Lines**，扩展名 `.linbak.gz`：

| 记录 | 内容 |
| --- | --- |
| `meta` | 格式版本、库名、创建时间、表顺序 |
| `ddl` | 每张表的 `SHOW CREATE TABLE` 原样结构 |
| `rows` | 列名 + 数据块，`BLOB` 以十六进制编码 |
| `trigger` | 触发器定义 |
| `end` | 各表行数与汇总 |

关键设计：

- **一致性快照**：`START TRANSACTION WITH CONSISTENT SNAPSHOT`，
  备份期间不阻塞业务写入，读取的是同一时点的数据。
- **按字节切块**：图片单行可能超过 6 MB，批次按估算字节数切分，
  避免恢复时单条 `INSERT` 超过 `max_allowed_packet`。
- **表顺序**：按外键依赖排序，被引用的表先建，自引用/环自动兜底。
- **失败清理**：中途失败会删除半成品文件，不会留下无法恢复的残包。
- **权限隔离**：`backup.view` 只能看，`backup.manage` 才能备份/下载/删除/演练。

## 2. 配置项

全部可选，默认值即可用。写入 `serve/.env` 或部署平台环境变量。

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `LINBLOG_DB_BACKUP_DIR` | `serve/storage/db-backups` | 备份目录；Railway 建议挂卷到 `/data/db-backups` |
| `LINBLOG_DB_BACKUP_RETENTION` | `7` | 保留份数，超出后每次备份自动清理最旧的 |
| `LINBLOG_DB_BACKUP_HOUR` | `3` | 每日定时备份的整点（0-23） |
| `LINBLOG_DB_BACKUP_CHUNK_SIZE` | `200` | 单表每次读取的行数，上限 5000 |
| `LINBLOG_DB_BACKUP_MAX_CHUNK_BYTES` | `2 MB` | 单块序列化字节上限，需小于 `max_allowed_packet` |
| `LINBLOG_DB_DUMP_TIMEOUT_MS` | `600000` | 单次备份/恢复超时（10 分钟） |
| `LINBLOG_DB_BACKUP_MAX_BYTES` | 未设置 | 备份目录容量上限；设置后设置页显示告警条 |
| `LINBLOG_DB_BACKUP_WARN_PERCENT` | `80` | 容量告警百分比 |

> `LINBLOG_DB_BACKUP_MAX_BYTES` 未设置时不做容量告警，只展示实际体积。
> 生产环境建议设置，例如 `4 GiB = 4294967296`。

## 3. 日常操作

### 3.1 自动备份

服务启动后延迟 3 分钟执行首次备份，之后每天在 `LINBLOG_DB_BACKUP_HOUR`
（默认 03:00）执行，成功后自动按保留份数清理。

日志关键字：`[DBBackup]`。

### 3.2 后台手动备份

系统设置 → 系统信息 → 数据库备份：

- **立即备份**：同步生成一份备份
- **恢复演练**：还原到临时库验证后自动删库
- **下载**：下载 `.linbak.gz` 到本地
- **删除**：删除单份备份
- **清理过期**：手动执行保留策略

### 3.3 命令行

```bash
# 手动备份（不需要启动 Web 服务）
cd serve
npm run db:backup

# 恢复演练：还原到独立库并保留，供人工核对
npm run db:restore -- linlog-20261030-030000.linbak.gz --drill

# 恢复到指定验证库
npm run db:restore -- linlog-20261030-030000.linbak.gz --target linlog_verify

# 真正覆盖当前库（会二次确认；非交互环境需 --force）
npm run db:restore -- linlog-20261030-030000.linbak.gz
```

核对恢复库与源库是否一致：

```bash
node scripts/verify-restore.js linlog_verify
```

核对内容：逐表行数、`image.data` 的 SHA-256 与 `checksum` 比对、
已发布文章数量。`db_backup_log` 会跳过（备份后才写入本次记录）。

## 4. 隔离恢复演练（每月一次）

目标：证明备份**真的能恢复**，而不是只看到文件存在。

1. 在后台点击某份备份的「恢复演练」，或在命令行执行 `--drill`。
2. 演练库名形如 `linlog_drill_<6位随机>`，与生产库完全隔离。
3. 核对以下三项：
   - 表数量与行数
   - `image` 表 BLOB 校验和
   - 抽查已发布文章正文/封面
4. 后台演练会自动删除临时库；命令行 `--drill` 会保留，核对后手动删除：

```sql
DROP DATABASE `linlog_drill_xxxxxxxx`;
```

建议把每次演练结果记录到运维日志（时间、备份文件、表/行数、耗时）。

## 5. 故障恢复步骤

> 恢复会删除目标库现有表并重建，务必先确认备份可用。

1. **停止写入**：停止 Web 服务，避免恢复过程中产生新数据。
2. **先演练**：用 `--drill` 还原到临时库，跑 `verify-restore.js`。
3. **留后路**：对当前库再做一次备份，或导出快照。
4. **正式恢复**：

```bash
cd serve
npm run db:restore -- <备份文件名>
```

5. **重启并验证**：启动服务，检查登录、文章列表、图片显示、评论。
6. **补一次备份**：恢复后立即做一份新备份，作为新的基线。

### 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `max_allowed_packet` 报错 | 单块超过服务端上限 | 调小 `LINBLOG_DB_BACKUP_MAX_CHUNK_BYTES`，或用新版本重新备份 |
| `不支持的备份版本` | 备份格式升级 | 用对应版本的服务恢复，或先升级服务 |
| 恢复后图片 404 | 只恢复了数据库，没恢复 `serve/data/files` | 文件与数据库需要各自恢复 |
| 临时库残留 | 清理阶段失败 | 手动 `DROP DATABASE`，检查数据库账号是否有权限 |
| 定时备份未执行 | 服务未运行或目录不可写 | 查看 `[DBBackup]` 日志，确认目录权限 |

## 6. 存储建议

- 备份目录放在独立挂载卷，不要与代码镜像同层，避免重新部署时丢失。
- 备份文件包含用户数据与密码哈希，**不要提交到 Git**
  （`.gitignore` 已排除 `serve/storage/db-backups/*`）。
- 单机备份不能防磁盘故障。建议把 `.linbak.gz` 再同步到对象存储或另一台机器，
  可复用现有 S3 配置思路，但数据库备份与附件备份应使用不同前缀。
- 图片 BLOB 会让备份体积随图片增长，定期关注设置页的容量告警。
